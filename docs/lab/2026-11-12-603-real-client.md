# Real 6.03r7 on `servers/modern`, and the post-merge client matrix, 2026-11-12

Loopback only: a Debian lab VM, with each run inside a private network namespace,
and a Windows 10 lab VM with no network adapter. Issues #23, #24 and #34.

## Builds

| Part | Commit | Build |
|---|---|---|
| This fork | `seihai` at `80a49f3` (CI Linux artifact), then this branch | GCC 14 + vcpkg `x64-linux`, `-DPACKET_LOGGING=ON` for the packet logs |
| This fork (Windows) | `seihai` at `1548ee3` | MinGW-w64, `-DPACKET_LOGGING=ON`, for the 2.x matrix |
| seihai-listserver | `b87208d` (Linux), `350a56e` (Windows) | `cargo build --release` |
| Real clients | Linux 6.03r7 (`G3D0511C`); Windows 2.22 and 2.31 | as shipped |

The Windows 6.03r7 could not be used: its Themida wrapper ends the process when a
DNS hook is attached, and the Windows VM has no other way to point the client's
built-in login host at loopback. The Linux 6.03r7 resolves that host through a
private `/etc/hosts` that maps it to 127.0.0.1.

## World

- `servers/login`: a copy of `servers/modern` named "Lab Login" on port 14900
  (the port 5.24+ clients dial first), `serverside = true`, and a level NPC that
  runs `serverwarp Lab Modern;` on `playerenters`. 6.x stays in its "Login" lobby
  mode until it is warped off a server whose name starts with "login".
- `servers/modern`: `basepackage.gupd` (`GRPKG001`, `NAME`, `VERSION`,
  `PLATFORM`) with `file *.gupd` in `foldersconfig.txt`. `labart.gpake` was made
  with `seihai-servertools gpak pack` from one image, `seihaigpak.png`, and is
  sent at login (`gpaks = labart.gpake`). The start level has an NPC with that
  image, which exists only inside the package. Also a GS2 weapon `-labgs2`,
  given to guests through `(defaultaccount).txt`. Its client part starts with
  `//#GS2`, and `serverside = true`, because the fork compiles GS2 only with its
  NPC-server.
- Both servers have `localhostlist = true`, so they register with the
  listserver, which then answers the login server's server-info request.

## #24: the weapon cache on the second login

Three logins in one server run, with the client's cache kept between them (from
the packet log):

| Login | Before this branch | With this branch |
|---|---|---|
| 1 | 197 `-labgs2`, 158 back, 140 (183 bytes) | 197, 158 back, 140 |
| 2 | 197, **158 back again**, 140 | 197, **no 158** |
| 3 | n/a | 197, **no 158** |

After the first login the client has
`weblevels/weapons/Lab%032Modern/%045labgs2.code`: `GRESCR01` and 151 bytes.
`seihai-servertools code show --key` decrypts it to the bytecode 140 carried.

- The 197 CRC before this branch was `0xd425d63c`, the CRC32 of the **plain**
  bytecode.
- The stored (encrypted) body's CRC32 is `0x4e195a69`.
- `seihai-servertools code pack` re-creates the file byte for byte.

So the client checks the CRC of what it **stored**, as the Windows 6.03 notes
said. This branch sends that CRC.
